Eight Gates

A harness is what makes an agent's work trustworthy: a gate that cannot lie, a definition of done that names a command, and a record that survives a restart. Every element below exists because something got through without it.

The mechanism

An agent cannot be the thing that decides it succeeded

The gate runs independently and reports an exit code; the agent never grades itself on anything a command can settle. What no command can settle goes to a reviewer in a context that did not write the code.

Why the gate has to reach the app

Passing the outer ring proves nothing about the inner one

The sequence

Each project fixes what the last one let through

The order is not a curriculum — it is a chain of failures. Read the middle column as the thing that went wrong, and the third as what had to be added because of it.

The elements

Nine parts, what each one catches, and what to write

This is the part you copy onto a new project. Each element below is drawn as the mechanism it actually is, followed by the smallest version worth writing on day one.

E1

The file map

Which files an agent reads before it starts, which it must write before it walks away, and the loop that turns one into the other.

Smallest version

Four files at the repo root, committed, existing exactly once: AGENTS.md, init.sh, feature_list.json, session-handoff.md. Add BASELINE.md before you write a line of code.

Audit what else is already sitting in the folder. In P01 three sample files in a data directory were read as a design spec — reasonably, because nothing said otherwise. Whatever is in the folder is the brief.

E2

init.sh — the gate

A ladder of checks, cheapest first, each one able to stop the run. The rung that matters is the last one, and it is the one most harnesses never write.

Smallest version

Start with rung 5 and nothing else. One command that drives a real user action, prints what came back, and compares it.

# the assertion must print the numbers it compared
OUT=$(SMOKE=1 node ./scripts/smoke.js)
echo "$OUT"                    # -> ROUNDTRIP: {"chunks":5,"citations":2}
if [ "$(echo "$OUT" | jq '.citations')" -lt 1 ]; then
  echo "FAIL: citations=0, expected >=1. qa-service.ts caps excerpts at 200 chars."
  exit 1
fi

Then watch it fail. Break the thing on purpose, run it, and read which rung produced the red. A gate you have not seen fail is not a gate — and "it failed" is not "it found the bug".

E3

AGENTS.md — the contract

Three blocks, and nothing else at the top level. Everything longer lives in a linked doc, because context spent on the entrypoint is context not spent on the work.

Why the Hands-off list is not optional

Most harnesses write down what the agent may do and never what it must not touch. On manual runs a human catches the overreach, so the gap stays invisible until nobody is watching. No written constraint, no constraint.

E4

Evidence, and the Trust loop

A status field is a claim somebody typed. In P03 a checked-in list was wrong in both directions at once — features marked done that were dead, and features marked missing that already worked.

  C -->|"command agrees"| D["believe it"]

Smallest version 
{ "id": "document-import", "status": "not-started",
  "evidence": null, "testedAt": null }

An empty field with a specific question is much harder to fill with nothing than a paragraph is. Given the Trust rule, one agent ran the gate against eleven pass entries, found the app dead, fixed it, and annotated the false claims rather than quietly overwriting them.

E5

Continuity across the boundary

The context window ends. Everything the agent worked out is gone unless a file caught it — and the next session must not simply believe what it finds.

Smallest version — the one un-fakeable field 
## Last ./init.sh result   <- paste the real output, not a summary
## Did I verify what I inherited, or trust it?
## What's half-done          <- exactly where I stopped
## Decisions I made          <- so the next session does not re-argue them
## Anything the repo was WRONG about
## Next step                 <- the single next thing

One field must demand a command's output. That is the field that cannot be filled from memory, and it is why the form works.

E6

Observability — a size, not a count

The gate tells you something is broken. Logs are what tell you where. A count says the loop ran; only a magnitude says it did anything.

Smallest version

Send logs to a stream a pipe can capture, not a human-only console. Then run this test: read the logs of a broken tree and a working tree, and name which is broken and which function — without opening the source. If you cannot, the logs are decoration.

And write failures for the agent: not Test failed, but Test failed: POST /api/reset returned 500. Check EMAIL_SERVICE_URL in .env. Template expected at templates/reset.html.

E7

Boundaries — enforce, don't describe

An architecture rule in a document is a rule nobody runs. The same rule as a sub-second script inside the gate names the file and the line.

The trap when you test it

In P04 an unused banned import was added to prove the boundary script worked. The gate went red — and the boundary script had never executed, because the type checker caught the unused variable first. A red gate proves nothing until you have read which step produced the red, including when you are the one testing the check.

E8

The reviewer — isolation is a file operation

For the part no command can settle, the scorer must not be the author. And the way you make that true is by controlling what is in the directory, not by asking nicely.

Smallest version — three files, three calls

brief.md (requirements as observable behaviour, plus "a filled rubric is part of done") · rubric.md (5–8 criteria, blank) · revise.md (apply every required revision; record disagreement, do not act on it). Then generate → review in a fresh context → revise.

Two lines make the rubric work: every score below the top must name a line, an input or an interaction, and top means a reviewer would merge it without comment. Without the first you collect vibes with numbers attached; without the second everything is one below top.

E9

The removal test

Every trigger you will ever write adds a step. Without one that removes, a harness grows until somebody comments it out — and then you have none.

What the measurement actually said

P04 ran exactly this on the observability step: same broken app, one agent with a structured logger and one without. 58s to the fix without it, 52s with. Three files read either way. Same root cause, same fix. A null result — and the step is still in the playbook.

A null result is permission to argue for deletion, not an instruction to delete. Write down what the run could not settle: that one was n=1, and the bug was obvious enough that neither arm needed the logger.

Three clocks

Setup runs once. Two other things never stop.

How to use it

Day one, in order, on a project that has none of this

  1. Interview the human — do not infer it from the code.The question that matters: what is ONE real thing a user does that proves this works, and what does it give back that a script can compare? If they cannot answer, that is the most important finding of the day.
  2. Measure the ground and write it down.Run the build yourself. Record verbatim errors in BASELINE.md. Audit every claim already in the repo against a real command.
  3. Write the gate, and watch it FAIL.E2. One real user action end to end, and the assertion prints the numbers it compared.
  4. Define done as a command in AGENTS.md.E3. Plus the Trust rule and the Hands-off list.
  5. Give every feature an empty evidence field.E4. An empty field with a specific question is much harder to fill with nothing than a paragraph is.
  6. Add the memory: a handoff form and a per-feature log.E5. One field must demand a command's output.
  7. Write the map — then enforce it.E7. Break each rule on purpose and watch the script name the file.
  8. Break something on purpose, and keep both trees.Show three exit codes: broken → non-zero, working → 0, and compiles cleanly but dead at runtime → non-zero. The third is the whole point. The two trees become the fixtures for E9.

If you only have time for two: BASELINE.md and init.sh — with a product check in it.

Build the smallest gate that catches a real break. Add a step only when a real failure has slipped through it. Four steps that run every time beat twelve that get commented out.

Self-review was accurate on everything checkable and generous on everything else. One agent found a real defect in its own work, fixed it — and scored itself 4.6 both before and after. The generosity is in the number, not the prose.

The next floor · loops

The same agent, restarted on a trigger, with no human between runs

Unearned

No run here was a loop, and none had two agents working at once. Everything in this section and the next is structure, not measurement — except the four facts explicitly marked measured.

L1

What actually changes

Not the agent, and not the gate. What moves is you — from inside the cycle, where every step waits on your prompt, to outside it, reading a file.

The readiness test

Not "do I have a scheduler". This: if you had to write the loop's brief tonight, would every line be a copy-paste out of files that already exist? An empty row below is where the loop will fail unattended.

L2

goal.md — the brief, and it is a readout

Seven sections. Six of them already exist somewhere in the harness; assembling the file is ten minutes. If they do not exist, no amount of loop tooling helps.

Four stop conditions, not one 
## Stop Conditions
- all acceptance criteria pass          <- the happy path
- max turns reached: 20
- no progress for 3 consecutive rounds  <- same error keeps appearing
- blocked, and cannot resolve alone     <- missing dep, env problem

Measured: a stop condition is an exit code, never a duration. Stopping a run at the right moment took three attempts here with a human watching — a clock gave both "finished everything in 6m54s" and "zero files written" on consecutive tries. Counting file edits worked. A loop has nobody watching at all.

L3

The round — maker, checker, state

E8 running every round instead of once. The two agents never talk directly; the state file is the handoff, which is what makes a round resumable after a crash.

L4

The six primitives

Five things on the ring, and one underneath it. Drawing external state as a sixth peer is the mistake — it is the floor the other five stand on.

L5

The ladder, and what it costs you

Five rungs, and the returns are front-loaded. Level 1 is one file and a stop condition; level 5 is a fleet you cannot personally read the output of.

Four costs that arrive quietly

Verification debt — "looks fine" quietly replaces "confirmed". Fix: stop conditions machine-checkable, always.  Comprehension rot — the loop ships faster than you read. Fix: fast loops need fast reading.  Cognitive surrender — you stop having opinions about the output; the loop cannot tell the difference, you can.  Token blowout — context grows roughly quadratically per turn.

Only the last one is a day-one problem, and it lands back on the harness: keep AGENTS.md a short entrypoint that links out, keep state files summary-first, put each fact in one place. A harness already near the context limit on a single manual run has no headroom to iterate.

The floor above that · graphs

More than one agent, plus a written answer to where a failure goes back to

G1

A graph is the loop, opened out

Not a new invention. The rollback edges were always there — the agent just "remembered" them, inside a context nobody else could read.

G2

Why it works: shared state, private context

The mechanism people miss. A graph does not just split the work — it splits the context, and shares only a file. That is also why E8's isolation rule scales up unchanged.

graph.md — one file, four things 
## Diagram        a mermaid flowchart
## Nodes          name | responsibility | in | out | agent or code?
## Edges          from | to | condition | is it a rollback?
## Shared state   field | who writes it | who reads it
## Routing        current node | condition | next node

Draw it once for a workflow you already run, and look for one edge you did not know existed — a path that lived in an agent's head and was never written anywhere. That edge is the whole return on the exercise.

G3

Do you actually need one

Five criteria, and you need three before drawing. The list matters less than the tiebreaker attached to it.

[ ] 1 · the task splits into genuinely independent units
[x] 2 · there are branch or rollback paths          <- the one that decides it
[ ] 3 · intermediate state is worth checkpointing
[ ] 4 · every node has an automatically checkable definition of done
[ ] 5 · coordination benefit beats coordination cost

scored below three? what you needed was a better script.

Scale is not the criterion — branches are. A twenty-step linear pipeline is a script, however long it is. Five nodes with a real rollback and an approval is a graph.

By that test, everything measured in Projects 01–05 was a linear three-call pipeline: generate, review, revise. No branch, no rollback, no approval node. None of it needed a graph — which is the honest reason this section is short.

G4

The two things everyone skips

Both are about the boundary between the graph and reality, and both get dropped first because neither one makes the diagram look better.

Anchors

the only thing that can say "the number moved, the world did not"

  • Real outcomes, ground-truth data, human spot-checks — something outside every loop in the graph.
  • Without one, a network of loops is a resonance of mutual drift: every node hits its target and the thing they were built for gets worse.
  • Your version already exists in miniature: the product check in init.sh is an anchor. It is the one step that touches the real thing instead of a proxy for it.

The orchestration tax

starting an agent is a keystroke; closing the loop on one is not

  • Launching is cheap. Someone has to read what came back and reconcile it with what the others touched — and there is one of you.
  • A graph runs more agents in parallel. Your judgement does not parallelise, so adding nodes optimises the part that was never the bottleneck.
  • This is why the ladder in L5 tops out where it does, and why serialise first, isolate second is the only measurement here that touches the question.

A loop hides the problem inside the loop. A graph puts the problem on paper.

Which is the point of both sections: neither floor is new tooling. They are this playbook, finished — and then wired together.
