## Important discovery: preload script was silently dead (fixed)

This wasn't in any previous handoff and cost most of this session to
find, so read carefully if `window.knowledgeBase` ever comes back
`undefined` again.

**Symptom**: `window.knowledgeBase` was `undefined` in the renderer even
though `preload.ts` correctly calls `contextBridge.exposeInMainWorld`,
the compiled `dist/preload/preload.js` looked correct, and the preload
path computed in `main.ts` existed on disk. No error was thrown anywhere
visible (`page.on('pageerror')`, main process stdout/stderr) -- the
preload script just never ran.

**Root cause**: Electron 33 defaults `webPreferences.sandbox` to `true`.
In a sandboxed renderer, the preload script's `require()` is restricted
to a small builtin allowlist (`electron`, `events`, `timers`, `url`,
etc.) -- it **cannot** `require()` arbitrary local project files. This
project's `preload.ts` does `import { IPC_CHANNELS } from
'../shared/types'`, which compiles to `require("../shared/types")`.
Under the sandbox, that require fails and aborts the whole preload
script *before* `contextBridge.exposeInMainWorld` runs -- silently, with
no error surfaced to the renderer or to Electron's normal error events.
(Confirmed via bisection: a trivial preload with no local requires
worked fine under the same sandboxed webPreferences; adding a
`require('./shared/types')` reproduced the exact failure in isolation.)

**Fix applied** (`src/main/main.ts`, `createWindow()`): added `sandbox:
false` to the `BrowserWindow`'s `webPreferences`, alongside the existing
`contextIsolation: true`. This restores full Node `require` inside the
preload script while keeping the renderer's main world isolated from
Node/Electron internals (contextIsolation is the setting that actually
matters for the security boundary here). See the comment left in
`main.ts` at the `sandbox: false` line.

**If revisited**: the "correct" long-term fix, if someone wants the
sandbox back on, is to bundle `preload.ts` into a single dependency-free
file (e.g. via esbuild/vite) so it has no local `require()`s at
runtime -- inline the `IPC_CHANNELS` constants directly into the
preload bundle. Out of scope for this session; `sandbox: false` is a
reasonable, standard choice for a `contextIsolation: true` +
`nodeIntegration: false` app like this one.

## How features were verified (for reproducibility)

No project skill existed for running this Electron app headlessly. I
installed `playwright-core` (`npm install --no-save playwright-core`,
NOT saved to `package.json`/`package-lock.json` -- confirmed clean
afterward) and drove the built app with a throwaway Playwright
`_electron` script under `xvfb-run -a`. `tmux` is not installed in this
container, so I couldn't follow the `run` skill's REPL-driver pattern
verbatim -- used a plain sequential Node script instead of a REPL.
System libs for Electron under xvfb (`libnss3`, `libgbm1`, `libgtk-3-0`,
etc.) were already present; no `apt-get` needed.

Key gotchas if you rebuild this driver:
- `xvfb-run -a node script.mjs` must be run with cwd `/work` (or
  `node_modules/playwright-core` won't resolve for an ESM import).
- Electron's chrome sandbox needs `--no-sandbox` in `args` (container has
  no `CAP_SYS_ADMIN`) -- unrelated to the `webPreferences.sandbox` issue
  above, don't conflate the two.
- To test persistence across a real restart, launch two separate
  `_electron.launch()` processes with the **same** `HOME` env var
  pointing at a scratch directory (so `app.getPath('userData')`
  resolves to the same place both times), calling `app.close()` on the
  first before launching the second.
- Clicking a list row via `document.querySelectorAll('div')` + text
  match needs care: `find()` on document-order divs returns the
  *outermost* matching ancestor first (since parent textContent
  includes all child text), not the actual clickable leaf row. Find a
  leaf div (`.children.length === 0`) whose own trimmed text equals the
  target, then click `.parentElement`.
- I did not build a persistent driver script or `.claude/skills/`
  entry for this -- the throwaway script was deleted after use. If this
  project needs headless UI verification again regularly, it's worth
  running `/run-skill-generator` to capture the sandbox/HOME/click
  gotchas above as a real project skill.

  to `DocumentService` directly.
